# Changelog

snakeboot follows [semantic versioning](https://semver.org/). While the version starts with `0.`,
a minor release may break the API: pin `snakeboot>=0.14,<0.15`.

## 0.14.0

- `snakeboot.stereotype`: an application declares its components in snakeboot's terms, like the annotations of
  `org.springframework.stereotype`, and no longer imports wireup. `@service` (a use case), `@repository` (the adapter
  of a repository port) and `@component` (anything else) make a class a component: built once, its dependencies by
  type. They do the same; the name says what the class is, and `stereotype_of(cls)` or
  `ComponentScan.classes_marked(STEREOTYPE_ATTRIBUTE)` tells an architecture test. `as_type=` names the port others
  ask for and `qualifier=` tells two components of one type apart, as wireup's `@injectable` does.
- `@bean` declares a function that builds a component, like a `@Bean` method; `Qualifier("name")` in
  `Annotated[...]` asks for the component with that qualifier, like `@Qualifier`.
- Nothing breaks: wireup's `@injectable` and `Inject(qualifier=...)` keep working, also next to the stereotypes, so an
  application moves when it suits. To move: `from wireup import injectable` becomes
  `from snakeboot.stereotype import service` (or `repository`, `component`), `@injectable` on a function becomes
  `@bean`, and `Inject(qualifier=X)` becomes `Qualifier(X)`.
- New refusals, when the module is imported: a stereotype on a function (`InvalidComponentError`, which names `@bean`),
  `@bean` on a class, and a class declared `as_type=` an abstract class it does not extend. A Protocol is not checked.
- The messages of a `@scheduled` or `@rabbit_listener` method on a class that is no component say `add @component`.
- The README says what an application shares with snakeboot: Pydantic, for a request body, a message and a `Section`.

## 0.13.2

- A table of snakeboot's own is part of the schema only once a method needs it, as a starter's table in Spring Boot:
  `snakeboot_event_publication` once the application has an `@application_module_listener`,
  `snakeboot_scheduler_lock` once it has a `@scheduler_lock`. In 0.13.0 and 0.13.1 the database of every
  `@application_test` demanded both of every application with `[database]`, so one without those methods, whose
  migrations rightly lack them, stopped every test with `The migrations do not build the tables of the entities`;
  and `make_migration` wrote them into its first migration whether it needed them or not. Spring Boot has no
  `event_publication` or `shedlock` table before Spring Modulith's or ShedLock's starter either. Migrations that do
  create them still may: a table no entity needs is left alone.
- `@entity(..., needed_by=...)` names the mark of the methods that need a library's table, which snakeboot's own
  tables use (`APPLICATION_MODULE_LISTENER_ATTRIBUTE`, which `@application_module_listener` now leaves besides the
  listener's mark, and `SCHEDULER_LOCK_ATTRIBUTE`); `EntityDescription` has the field `needed_by` (None by default).

## 0.13.1

- `Version()` documents its form for a `NOT NULL` column, as in a schema another tool made:
  `Annotated[int, Version()] = 0`; a new entity still gets 1. `Annotated[int | None, Version()] = None` makes a column
  that may be empty, which the schema checks report against a `NOT NULL` one.
- A `%` in a migration (in `LIKE 'C%'`, a default or a comment) no longer stops `migrate` on PostgreSQL: the script
  goes to the driver without parameters, so psycopg no longer reads `%` as the start of a placeholder.
- `DatabaseProperties(...)` built in code takes a key given as `None` as no key: `file=None` next to a server's keys,
  or the server's keys as `None` next to `file`, is no longer refused as "a server or a file, not both".
- A web slice (`@web_test`) runs no migrations, like `@WebMvcTest`, which configures no datasource: its SQLite in
  memory has only the tables of the entities in the slice (snakeboot's own), made from the entities. In 0.13.0 every
  slice ran every migration of the application, so a `V1` from `pg_dump` in PostgreSQL's own SQL
  (`GENERATED BY DEFAULT AS IDENTITY`, `::text` casts), which SQLite refuses, stopped every `@web_test`, and it takes
  no `database=`. A module slice (`@application_module_test`) still runs every migration of the application, as
  0.13.0 does, on SQLite or with `database=PostgreSQLContainer()`. What a controller, an advice or the authentication
  needs from outside the slice, a repository too, is a `MockComponent`, as in Spring.
- An environment variable named like a section is no longer read as its whole table: only `SECTION__KEY` and
  `SECTION__TABLE__KEY` set a value, as the README says, like Spring Boot's binder, which ignores a plain value at a
  name that has nested properties. Before, `AI_AGENT=claude-code_...`, which coding agents set, stopped an
  application with an `[ai_agent]` section at start-up with pydantic-settings' `error parsing value for field
  "ai_agent"`, and a host's `SERVER`, `DATABASE` or `CACHE` would have done the same, or made an absent optional
  table present.
- `python -m myapp help`, `help <command>` and no command list the commands again when a value is missing or
  invalid, as 0.7 promised: which commands there are depends on the tables the files and the environment have
  (`migrate` comes with `[database]`), not on their values (`sections_with_a_table`). Any other command whose
  configuration is invalid stops with exit status 1 and one line per problem that names the key and the variable
  that sets it, `myapp migrate: database.password is missing: set it in application.toml or DATABASE__PASSWORD`,
  instead of pydantic's traceback; so does a missing `application.toml`. Outside the command line (`TestApplication`,
  `load_configuration`, the server's processes) the configuration still raises pydantic's `ValidationError`, now
  with those sentences as notes (`configuration_problems`).

## 0.13.0

What an application needs to move to snakeboot with its production data, and tests that run the real migrations:

- Connecting to the PostgreSQL server of `[database]` gives up after 10 seconds, like the `connectTimeout` of
  PostgreSQL's JDBC driver. Before, psycopg waited 130 seconds per address, and on Windows even a refused connection
  failed only then: `migrate` or the start seemed to hang for over four minutes when the server was not running.
- A `@test_component` nested in a test class holds for that class only, like a static nested `@TestConfiguration`: a
  hand-written fake for a few tests, which wins over the project's test component of the same component. A pytest
  class nested in it sees it too, as a JUnit `@Nested` class does, and the innermost wins; beside a `MockComponent` of
  the same component in the same class, it stops the test. The source scan no longer counts a class nested in a class
  or a function as one of the project's test components or applications. **Breaking:** a `@test_component` grouped in
  a plain class (`class Doubles:`) held for every test before; it now holds for that class only, so move it to the
  module's top level.
- A `@rabbit_listener` message that keeps failing is no longer lost (#1), as in Spring Boot: the optional table
  `[rabbitmq.listener.retry]` (`max_attempts`, `initial_interval`, `multiplier`, `max_interval`, like
  `spring.rabbitmq.listener.simple.retry.*`) tries it again with exponential back-off, and
  `@rabbit_listener(..., dead_letter=True)` declares the durable queue `<queue>.dead-letter`, where RabbitMQ then
  moves what the listener refuses for good, as Spring's `RejectAndDontRequeueRecoverer` does with the queue's
  `x-dead-letter-exchange`. `RejectAndDontRequeueError` and an unreadable body are still refused at once, without a
  retry. Without the table a message is tried three times, a second apart, as before; during a pause the connection
  keeps answering the broker's heartbeats.
- The start-up declares the exchange, queues and binding of every listener before any consumes, and a declaration
  RabbitMQ refuses stops it with `AmqpDeclarationError`, instead of a listener that tries again every five seconds
  as if the broker were down. A queue that exists without the dead-letter queue its listener now asks for is one:
  the message says how to migrate it (delete the queue while it is empty, or use a policy), and so does the README.
- `InProcessRabbitTemplate.dead_lettered` holds what a listener with `dead_letter=True` refused, and every
  `RefusedMessage` has its `dead_letter_queue` (None without one).
- **Breaking:** on SQLite in memory, `@application_test` runs the application's own migrations instead of creating
  the tables from the entities, like Flyway on H2 in Spring Boot's tests: the scripts `migrate` runs, once per
  process, in a template database that every test copies. First the migrated schema is compared with the entities,
  like `ddl-auto=validate`: a table, column, NOT NULL or index the migrations lack stops every test, with the SQL
  `make_migration` would still write (the types are compared on PostgreSQL only, as SQLite takes any type name). A
  migration that SQLite rejects stops them too, with its name, and so does a generated key that SQLite would not
  number (declared otherwise than `INTEGER PRIMARY KEY`, such as `BIGSERIAL`). To move: let `make_migration` write
  what the migrations lack, snakeboot's own tables included; an application whose migrations need PostgreSQL's own
  SQL runs its tests with `@application_test(database=PostgreSQLContainer())`. An application without migrations
  keeps the tables of its entities.
- A slice (`@web_test`, `@application_module_test`) runs every migration of the application, on SQLite and on
  PostgreSQL alike, as `migrate` does, instead of those of the contexts it starts: snakeboot's own tables, or a table
  another context's migration changes, are there.
- The SQLite of a test keeps a UUID as text with its dashes: in a column a migration declared `UUID`, which SQLite
  reads as a number where it can, `UUID(int=7)` would have become 7.
- `in_memory_database(entity_types, migrations=...)` returns a database on that schema, `in_memory_database()` an
  empty one as before; `postgresql_database(image, entity_types, migrations=...)` runs the migrations given.
- A test that replaces the `Database` with its own gets it as it gave it: snakeboot creates no tables in it.
- A database whose schema was made before its migrations is baselined (#12), like Flyway's `baseline-on-migrate`
  with `baseline-version`: with the optional `[database] baseline_version = 1`, `migrate` finds tables but no history
  of migrations (or an empty one), records V1 and every migration before it as run without running them, and prints
  `Baselined V1__...sql`; then it runs the later ones. A fresh database runs every migration, the in-memory and
  PostgreSQL databases of the tests included, and a database with a history is never baselined. A baselined row keeps
  the checksum `baseline`, which is never compared with the script, as Flyway skips its baseline row. A
  `baseline_version` that names no migration stops `migrate`; without the key nothing changes, except that a first
  migration that fails on tables made before the migrations says to set `baseline_version`.
  `SchemaMigrations.migrate()` returns a `MigrateResult` (`baselined`, `applied`) instead of the list it ran.
- On PostgreSQL, `migrate` resets the session's settings after every script (`RESET ALL`). A script as `pg_dump`
  writes it begins with `set_config('search_path', '', false)`, after which neither the history row nor the next
  script found its tables.
- An endpoint receives an uploaded file (#10), like Spring's `MultipartFile`: a parameter of type `UploadedFile`
  (`filename`, `content_type`, `size`, `content`) is filled from the part of the same name of a `multipart/form-data`
  form, whose other fields fill the endpoint's other parameters outside the path. The OpenAPI document shows the
  form, with a file picker in Swagger UI. `snakeboot[web]` brings python-multipart for it.
- The optional key `[server] max_upload_size`, like `spring.servlet.multipart.max-file-size`: a number of bytes or a
  size such as "20MB" or "20MiB"; without it, 1 MiB, Spring Boot's default. A larger file never reaches the endpoint:
  it raises `UploadTooLargeError`, which an advice answers, and without one the API answers 413
  `{"code": "upload_too_large", "detail": ...}`. An `application.toml` without the key needs no change; code that
  builds a `ServerProperties` itself passes `max_upload_size=None`, as it passes `retry=None` to
  `RabbitListenerProperties`.
- An endpoint answers with a file (#11), like Spring's `ResponseEntity<Resource>`: it returns
  `FileDownload(content, media_type, filename=..., inline=...)`, and the answer holds the bytes, the media type as
  `Content-Type` and `Content-Disposition: attachment` (or `inline`) with the file name, in UTF-8 in `filename*` when
  it is not plain ASCII and as near as ASCII gets in `filename` (RFC 6266), and `X-Content-Type-Options: nosniff`.
  `@route.get(..., produces="application/pdf")`, like `@GetMapping(produces = ...)`, names the media type in the
  OpenAPI document, which shows a binary answer (of any media type without it). With `[cors]` the script of an allowed
  page may read `Content-Disposition`.
- The start stops on an `UploadedFile` that is not one plain parameter (a list, an optional file, a default), on an
  upload on a GET or DELETE, and on `produces` on an endpoint that answers with something else than a `FileDownload`.
- An entity describes the unique constraints and indexes of an existing schema with their own names (#7), so
  `make_migration` and the schema checks of the tests no longer propose to drop them:
  `@entity(..., unique_constraints=(UniqueConstraint(name, *columns),))`, like JPA's `@UniqueConstraint`, and `Index(name, *columns, unique=True, where="...")`, a unique
  index, partial with `where` (whose condition the schema checks leave alone). On PostgreSQL a unique constraint
  (Django's `UniqueConstraint`) and a unique index (one with a `condition`) are different objects: each compares
  equal to the one the entity declares, and not to the other.
- `ForeignKey("funding_call.id", on_delete="cascade", name="...", deferred=True)` on a column, like `@JoinColumn`
  with `@ForeignKey` and Hibernate's `@OnDelete` (#8). `make_migration` writes it, and the schema check on PostgreSQL
  compares its columns, its target, its `ON DELETE` and whether it is `DEFERRABLE INITIALLY DEFERRED` (as Django
  declares every foreign key there), but not its name. The database in memory of a test enforces it as production
  does, since SQLite's foreign keys are on: deleting a row cascades, or is refused while rows refer to it. There are
  no relationships: a repository loads the rows that refer to another. The column it refers to is an entity's of the
  same application, or of the same slice in a test; another stops the start (`InvalidEntityError`), as does
  `on_delete="set null"` on a field that is never empty.
- `Annotated[int, BigInt()]` and `Annotated[int, SmallInt()]` make a BIGINT and a SMALLINT, like Java's `long` and
  `short` (#9): an amount past 2,147,483,647 fits, and Django's `BigIntegerField` and `SmallIntegerField` compare
  equal instead of being altered to INTEGER. SQLite keeps every whole number alike.
- A listener may inject a use case that publishes events (#13), as a listener between two bounded contexts does:
  listener -> use case -> `ApplicationEventPublisher` -> every listener was a cycle that stopped the start, and the
  way out was a lookup in the `ApplicationContext` when the event arrived. As in Spring, the publisher now depends on
  no listener: it keeps them in an `ApplicationEventListenerRegistry`, and `ApplicationContext.refresh` builds every
  `@application_event_listener` once the container is built and registers it (`EventListenerMethodProcessor`, like
  Spring's), so a listener that cannot be built still stops the start, not the first event. A start that fails closes
  the context it began. `ApplicationEventPublisher.register(listeners)` adds listeners, and
  `refresh(..., prepare=...)` replaces components before the listeners are built, as `TestApplication` does with the
  `@test_component`s and the spies, which therefore reach the listeners. **Breaking:** a wireup container built
  without `ApplicationContext` registers its listeners itself, with
  `get(EventListenerMethodProcessor).register_listeners()`.
- `SPY` (`snakeboot.boot.testing`) as the double of a type in `TestApplication.start(overrides=...)` wraps the
  application's own component in a spy before anything that depends on it is built, like `@MockitoSpyBean`, so the
  spy records what a listener calls too: `overrides={PaymentPort: SPY}`. A `SpyComponent` of an `@application_test`
  passes it. `TestApplication.spy(T)` after the start still spies on what is built later, but not for the listeners,
  which were built when the application started.

Moving an application from 0.12:

| 0.12 | 0.13 |
|---|---|
| a test on SQLite in memory got the tables of the entities | it runs the application's migrations and checks the entities against them: let `make_migration` write what the migrations lack, or test with `PostgreSQLContainer()` when they need PostgreSQL's own SQL |
| a slice ran the migrations of its own contexts | it runs every migration of the application |
| a `@test_component` inside a plain class held for every test | it holds for that class only: move it to the module's top level |
| a listener was built when the publisher was first needed | every listener is built when the application starts, for a command such as `migrate` too |
| a wireup container built without `ApplicationContext` gave the publisher its listeners | it calls `get(EventListenerMethodProcessor).register_listeners()` |
| `SchemaMigrations.migrate()` returned the migrations it ran | it returns `MigrateResult(baselined, applied)` |
| code that builds `ServerProperties`, `RabbitListenerProperties`, `RabbitListenerMapping` or `EntityDescription` itself | it also passes `max_upload_size`, `retry`, `dead_letter_queue` or `unique_constraints` |
| a refused declaration made a listener retry as if RabbitMQ were down | it stops the start with `AmqpDeclarationError` |

## 0.12.0

Tests in Spring Boot's style, without conftest.py, fixtures or settings:

- `@application_test`, like `@SpringBootTest`: every test it marks gets the application, started anew, and what it asks
  for by type, in its fields (a class) or its parameters (a function): `Autowired[T]`, like `@Autowired`;
  `MockComponent[T]`, a mock that replaces the component for one test, like `@MockitoBean`; `SpyComponent[T]`, the
  component wrapped in a spy, like `@MockitoSpyBean`; `Autowired[RestClient]`, a client of the REST API.
  `@application_test(application=..., profile=..., properties=...)` names the application, activates a profile and sets
  properties that win over every other source.
- `@test_component(replaces=ClockPort)`, like `@TestComponent` with `@Primary`: a class of the tests that replaces a
  component in every `@application_test`, built anew for each, and reachable by its own type (`Autowired[FixedClock]`).
- The application and the test components are found in the project's source on Python's path, as Spring Boot finds
  the `@SpringBootConfiguration`; the source is read, not imported, and `site-packages` is left alone.
- `when(mock.method).then_return(...)`, `then_raise`, `then_answer` and `verify(mock.method).called_once_with(...)`,
  `called_with`, `called_times`, `never_called`: Mockito, in the types of the port, so a type checker refuses an answer
  or an argument of the wrong type.
- `signed_in_as("ann", roles={"writer"})`, like spring-security-test's `jwt()`: the headers of a call by ann, which the
  application of a test accepts next to its own tokens; its own `@roles_allowed` decide.
- `snakeboot.pytest_testing`, the binding of `testing` to pytest: pytest loads its plugin through the entry point
  `pytest11`. `snakeboot[testing]` brings pytest.
- `@application_test(database=PostgreSQLContainer())`, like Testcontainers' `PostgreSQLContainer` with
  `@ServiceConnection`: the test runs on PostgreSQL in Docker. The application's own migrations build the schema
  once per process, in a template database that every test copies; first the migrated schema is compared with the
  entities, like `ddl-auto=validate`, and what `make_migration` would still write stops the tests, with that SQL.
  `snakeboot[testcontainers]` brings Testcontainers.
- `Autowired[PublishedEvents]`, like Spring's `ApplicationEvents` and Spring Modulith's `PublishedEvents`: every event
  the application published during the test, `of_type(AuctionClosed)`.
- With `[rabbitmq]`, a test's `RabbitTemplate` is an `InProcessRabbitTemplate`, like Spring AMQP's `TestRabbitTemplate`:
  it keeps every message in `sent` and hands it, as the same JSON, to the application's own `@rabbit_listener` methods
  whose queue a topic exchange routes it to, after the sender's commit; what a listener refuses lands in `refused`.
- `TestApplication.start(..., environment=TestEnvironment(profile=..., properties=..., database=...),
  test_components=...)`, `TestApplication.spy(T)`, `TestApplication.published_events`; `TestApplication.get` finds a
  double by its own type too; with `[cache]` a test gets an `InMemoryCache`; the API accepts the tokens of
  `signed_in_as`; `close()` drops the PostgreSQL copy of the test.
- `begin_configuration(..., profile=..., properties=...)` and `ApplicationContext.of(..., profile=..., properties=...)`;
  `ApplicationContext.refresh(..., additions=...)` adds wireup's injectables besides the modules;
  `ApplicationContext.replace_component` replaces a component of the built container, and names what it lacks.
- `snakeboot.rabbitmq.rabbit_listener_endpoints` finds the `@rabbit_listener` methods of an application, for the
  listener containers and the in-process template alike.
- Test slices: `@web_test`, like `@WebMvcTest`, starts the REST layer alone (the modules of the controllers, advices,
  authentication and sections), and `@application_module_test("auction_house.invoicing")`, like Spring Modulith's
  `@ApplicationModuleTest`, starts bounded contexts without the others. What a slice leaves out, a test gives as a
  `MockComponent`, which joins the container; a dependency nobody gave stops the test and names it.
  `TestApplication.start(..., only=WebSlice() | ModuleSlice(...))`.
- `snakeboot.component_scan.narrowed_application(application, modules)`: the application without those modules, its
  package, configuration and OpenAPI definition kept.
- What a module defines that the component scan excludes stays out of the container, even where a scanned module
  imports it: wireup registers a module's imports too, so an `exclude` let a component in through an import.
- `Autowired[LocalServer]` and `TestApplication.local_server()`, like `webEnvironment = RANDOM_PORT`: the application
  served over HTTP on a free port, with the lifecycle running; `server.url`, `server.port`, `server.client()`.
  `web_api(..., also_allowed_hosts=...)` lets it accept `127.0.0.1` besides `[server] allowed_hosts`.
- With `[oauth2]`, `Autowired[AuthorizationServer]` (`snakeboot.oauth2.testing`) signs real JWTs with a key of the test,
  `signed_in("carol", realm_access=...)`, which the application's own `JwtBearerAuthentication` checks and maps with its
  own `roles_of`. `JwtBearerAuthentication(properties, signing_keys=...)` takes the keys a test gives
  (`JwtSigningKeys`); without them, the issuer's key set, as before.
- `eventually(check, within=..., every=...)`, like Awaitility: tries a check until it holds, for code on a thread of its
  own.

## 0.11.1

- `migrate` on SQLite runs a script statement by statement in the migration's own transaction, so a failing script
  leaves no trace, as on PostgreSQL. 0.11.0 ran it with Python's `executescript`, which commits the open transaction
  first: the statements before the failing one stayed in the database while the history did not record the script,
  and the next `migrate` stopped on what was left. `snakeboot.sqlalchemy_data.sqlite.statements_of` splits a script
  where SQLite ends a statement, not at a `;` in a string, a comment or a trigger.
- The README renders again from the entity example on: a code block's closing fence had a sentence on its line.

## 0.11.0

- `[database]` is a PostgreSQL server or one SQLite file: `[database] file = "myapp.sqlite3"` keeps a service's
  database in that file, for a demo or a small tool on one machine. Every thread of the service shares it; a
  transaction takes SQLite's write lock when it begins (`BEGIN IMMEDIATE`), in WAL mode, and waits up to 30 seconds
  for another's, so threads that write at once wait for each other instead of failing. `migrate` and `make_migration`
  work on it in SQLite's dialect. A table with a server's keys and `file` stops the start.
- `snakeboot.sqlalchemy_data.sqlite`: `sqlite_file_engine` and `open_transactions_with_sqlalchemy`, which the database
  in memory of a test now shares.
- The migrations' history is read without SQLAlchemy's deprecated `Result.tuples()`: no more warnings.

|---|---|

## 0.10.2

- `snakeboot.sqlalchemy_data.testing`: the database in memory of a test lends its one connection to one thread at a
  time from inside SQLAlchemy's pool (`OneThreadAtATimePool`). 0.10.0 waited for it in the pool's checkout event,
  after the pool had already handed the waiting thread the record of the connection another thread held; that thread
  then never gave the connection back, and a test whose scheduler or listeners used the database next to it failed
  after ten seconds with "Another thread held the database in memory".

## 0.10.1

- `snakeboot.sqlalchemy_data`: a transaction's session holds every entity it read until the transaction ends, like
  JPA's persistence context. SQLAlchemy held an entity only while somebody else did, so an adapter that mapped a
  record to its domain object and let the record go read the row afresh at its next query, with a version another
  transaction had written meanwhile: a `Version()` never caught that lost update. A repository now hands out one object
  per row in a transaction, as the row was first read.

## 0.10.0

What most enterprise applications need from Spring Boot next: authorization, reliable events, optimistic locking,
the actuator, traces and structured logs, a lock for scheduled work, and CORS.

- `snakeboot.security` (standard library only): `Principal` moved here and has `roles` (`has_role`,
  `has_any_role`); `SecurityContext`, like `SecurityContextHolder`, holds the principal of the call in hand.
  `snakeboot.rest.Principal` is the same class.
- `snakeboot.rest`: `@roles_allowed("admin", ...)` on an endpoint or a controller, like `@RolesAllowed`: a caller with
  none of the roles is answered 403 `{"detail": "Forbidden"}`. An endpoint's own roles replace its controller's; roles
  on a public endpoint, or without a `BearerAuthentication`, stop the start. `BearerAuthentication.authenticate` may
  return a `Principal` with roles instead of an id. The web binding signs the caller in to the `SecurityContext` while
  the endpoint runs.
- `snakeboot.oauth2`: `JwtBearerAuthentication` returns a `Principal` whose roles are Keycloak's realm roles, its client
  roles for the audience and a plain `roles` claim; `roles_of(claims)` may be overridden.
- `snakeboot.data`: `Version()`, like JPA's `@Version`: an update holds only while the row has the version the entity was
  read with, else `OptimisticLockingFailureError`. `CreatedBy()` and `LastModifiedBy()` fill a `str | None` with the
  signed-in principal's name. A broken constraint is a `DataIntegrityViolationError`. `LockMode.PESSIMISTIC_WRITE_SKIP_LOCKED`
  is `SELECT ... FOR UPDATE SKIP LOCKED`.
- `snakeboot.events`: `@application_module_listener`, like Spring Modulith's `@ApplicationModuleListener`: after the
  commit, on the application's `TaskExecutor` (eight threads), in a transaction of its own, in the trace of the
  publisher. `ListenerMapping.delivery` (`Delivery`) replaces `ListenerMapping.after_commit`.
- `snakeboot.event_publication`: with `[database]`, the event publication registry, a transactional outbox like Spring
  Modulith's JDBC registry. The publisher's transaction writes one row of `snakeboot_event_publication` per module
  listener (the event as JSON); the listener's transaction deletes it. A failed or lost publication is delivered again,
  ten times at most, by a lifecycle component that also shows `snakeboot_event_publications_incomplete`. The optional
  table `[events]` (`EventsProperties`: `resubmit_every`, `in_flight`, `retry_after`, `max_attempts`) sets that timing,
  like `spring.modulith.events.*`.
- `snakeboot.scheduling`: `@scheduler_lock(name, at_most_for=..., at_least_for=...)`, like ShedLock's
  `@SchedulerLock`: one replica runs a turn, the others skip it. Every scheduled run is a trace of its own.
- `snakeboot.scheduler_lock`: with `[database]`, the locks as rows of `snakeboot_scheduler_lock`.
- `snakeboot.actuator` (wireup only): `HealthIndicator`, `ApplicationHealth` and `MeterRegistry` (counters, timers as
  histograms, gauges, in Prometheus's text format, without a client library). The database, Redis and RabbitMQ bring
  their indicators.
- `snakeboot.fastapi_web`: `/health` checks every indicator and answers 503 when one is DOWN; `/health/liveness` and
  `/health/readiness` for Kubernetes's probes; `/metrics` for Prometheus, with `http_server_requests_seconds` per
  method, route and status. Every call runs in a span of the caller's `traceparent`, or of a new trace. `[cors]`
  (`CorsProperties`) names the origins whose pages may call the API.
- `snakeboot.tracing` (standard library only): `TraceContext`, W3C Trace Context. The `RabbitTemplate` sends the
  `traceparent`, a `@rabbit_listener` continues it, and every log line carries the trace id.
- `[logging] format = "ecs"` (`LoggingProperties`) writes every log line as JSON in the Elastic Common Schema.
- `TestApplication` runs the `@application_module_listener` methods on the caller's thread. Its database in memory
  lets one thread at a time hold its one connection, so a call to the API, the scheduler, a listener and the
  registry's resubmission never begin a transaction inside another's (SQLite's "cannot start a transaction within a
  transaction").
- The README says where an application's files live: `application.toml` and its profiles in the application package
  (the package of the `@application_root` class, snakeboot's classpath root), migrations next to their entities,
  `static/` and `templates/` kept free for pages.
- `make_migration` writes the tables of snakeboot's own entities (`snakeboot_event_publication`,
  `snakeboot_scheduler_lock`) into the application's migrations.

## 0.8.0

snakeboot runs on FastAPI, SQLAlchemy and Alembic instead of Django, and an application sees none of them: its
entities, repositories, migrations and tests are in snakeboot's terms now too. 0.7 stays on the branch `release-0.7`.

- `snakeboot.application`: the application context, like Spring's `ApplicationContext`. It reads the configuration,
  builds wireup's container from the component scan, installs the transaction manager when there is a database, and
  runs the commands; it knows no framework. `snakeboot.boot` names the bindings: FastAPI for the REST API, SQLAlchemy
  with `[database]`, Redis with `[cache]`, RabbitMQ with `[rabbitmq]`. An application without a table imports none of
  them, and `python -m myapp help` answers without loading a web framework.
- `snakeboot.fastapi_web`: the REST API on FastAPI, under /api with Swagger UI at /api/docs and /health beside it.
  Controllers, advices, `Principal`, `BearerAuthentication`, `InvalidRequestError` and `ServerSentEvents` work as
  they did; a stream is documented as `text/event-stream`. `[server] allowed_hosts` is enforced by Starlette's
  `TrustedHostMiddleware` (`*`, `games.example.com`, `*.example.com`).
- `snakeboot.data`: entities and repositories, like Spring Data. `@entity` on a dataclass, with `Id`, `Column`,
  `Index`, `CreatedDate`, `LastModifiedDate`, `Json` (any JSON value; `Any` is JSON too) and `Vector`; `CrudRepository[E, ID]` interfaces whose methods are
  derived from their names (`find_by_status_and_join_deadline_less_than_equal`, `find_top_100_by_..._order_by_id_asc`,
  `count_by`, `exists_by`, `delete_by`, a `PageRequest`), `@query` for SQL, `@lock` for `SELECT ... FOR UPDATE`.
  snakeboot implements an interface when its module is imported; a method it cannot implement stops the start.
- `snakeboot.sqlalchemy_data` (extra `data`): the entities mapped to SQLAlchemy without the classes knowing it,
  `@transactional` on SQLAlchemy's session (a nested call is a savepoint), and migrations as plain SQL scripts next to
  the entities, like Flyway: `python -m myapp migrate` runs them once each, `python -m myapp make_migration "..."`
  writes the next one from what Alembic finds missing. PostgreSQL through psycopg; pgvector with the extra `vector`.
- `snakeboot.cache` and `snakeboot.redis_cache` (extra `cache`): a `Cache` of JSON values, in Redis with `[cache]`, in
  memory for a test.
- `snakeboot.boot.testing.TestApplication`: starts the application as it runs, with doubles for components and a
  database in memory whose tables come from the entities, and calls its REST API in the same process, like
  `@SpringBootTest` with `@AutoConfigureTestDatabase` and `TestRestTemplate`. Every test gets a fresh application.
- `run_lifecycle` is a `CommandLineRunner` of snakeboot's, and `help` lists snakeboot's commands apart from the
  application's.
- `ApplicationComponents` finds marked classes too, and `get` takes abstract classes and Protocols as mypy expects.
- wireup 2.13.1 or later: 2.13.0 cannot build a container in which a component depends on the event publisher of
  an application without listeners.
- Gone: `snakeboot.django`, `snakeboot.django_application`, `snakeboot.django_ninja`, `wsgi_application`,
  `DjangoConfigurer`, `ComponentScan.classes_extending`, the extras `django` and `ninja`, and `[server] secret_key`.

## 0.7.0

An application speaks snakeboot, not Django: its entry points, controllers, commands and configuration import
nothing of Django or Django Ninja any more, so snakeboot can bind another framework without changing them.

- `snakeboot.boot`: `run`, `wsgi_application` and `asgi_application`, where an application's entry points import
  them from. `snakeboot.django_application` still has them, as the binding that `boot` hands over today.
- `snakeboot.rest` knows no web framework. An endpoint takes no `request`: it takes path, query and body parameters,
  and a parameter of type `Principal` for whom the token belongs to, like `@AuthenticationPrincipal`. The body is the
  return annotation, `response=` only when it differs; `status=` sets the status of the answer, like
  `@ResponseStatus`; `public=True` opens an endpoint, like `permitAll()`. A route takes no other option. A method that
  takes `request`, a public endpoint that asks for a `Principal` and a `Principal` without a `BearerAuthentication`
  stop the start.
- `snakeboot.rest`: `ServerSentEvents`, like Spring's `SseEmitter`. An endpoint that returns it streams
  `text/event-stream`, uncached and unbuffered, with a heartbeat comment after 15 silent seconds and an end after 30
  minutes. `ServerSentEvents.watching(read, every=..., until=..., as_event=...)` reads a value in the call, then
  sends it whenever it changed; its reads run between fresh database connections. `ServerSentEvent` data that is no
  text is the JSON a REST answer would hold.
- `snakeboot.rest`: `InvalidRequestError`, like Spring's `MethodArgumentNotValidException`: a call that does not fit its
  endpoint (a missing field, a wrong type), with one `RequestProblem` per error. An advice answers it like any error,
  and `error_answer` makes it `{"code": "invalid_request", ...}`; without such an advice the framework answers 422 its
  own way.
- `snakeboot.django_ninja`: the REST API on Django Ninja (`rest_api`, `url_patterns`, `NinjaEndpointFactory`), which
  was part of `snakeboot.rest`. `ControllerScan(...).find()` returns the checked API without building anything.
- `snakeboot.command_line`: `CommandLineRunner`, like Spring Boot's, with constructor injection and argparse.
  `add_arguments` is a classmethod and `run_command(SelfPlayCommand, arguments, program=..., build=...)` parses before
  it builds, so `--help` and a wrong argument answer at once, whatever the command depends on.
  `python -m myapp self_play --games 20` runs the one its first argument names; `help` lists them next to Django's
  commands, those of its apps (`run_lifecycle`) included, and names the program `python -m myapp`.
  `CommandLineError` stops a command with a message and status 1.
- `snakeboot.configuration`: the table `[django]` is `[server]` (`ServerProperties`, environment `SERVER__*`), with
  the same keys. `DatabaseProperties` and `CacheProperties` lost `as_django_database` and `as_django_cache`;
  `snakeboot.django_application.django_settings` converts them.
- `snakeboot.component_scan` knows no Django: `DJANGO_ENTRY_POINTS` is `DEFAULT_EXCLUDE`, and `app_configs()` and
  `models()` are gone (`classes_extending("AppConfig")` finds what they found).

## 0.6.0

- `snakeboot.lifecycle`: components that start and stop with the server, like Spring's `SmartLifecycle`. A subclass
  of `Lifecycle` is a component; `ApplicationLifecycle` starts every one in phase order and stops them in reverse,
  then publishes `ApplicationReadyEvent` to the event listeners. A listener of that event that raises stops the
  start-up, as in Spring Boot.
- `snakeboot.django_application`: `asgi_application` answers uvicorn's `lifespan`, which Django's handler refuses, and
  runs the lifecycle around Django's handler; it returns a `LifecycleAsgiApplication` instead of Django's
  `ASGIHandler`. `python -m myapp run_lifecycle` runs the lifecycle without a web server until SIGTERM or SIGINT.
  Threads outside a request get their components and fresh database connections from `background_work`.
- `snakeboot.scheduling`: `@scheduled(fixed_rate=..., fixed_delay=..., initial_delay=...)`, like `@Scheduled`, on one
  thread. `[scheduling] auto_startup = false` (`SchedulingProperties`) keeps a process from running them.
- `snakeboot.rabbitmq` (extra `rabbitmq`): `@rabbit_listener` and `RabbitTemplate` on RabbitMQ through pika, like
  Spring AMQP, with the section `[rabbitmq]` (`RabbitProperties`); only an application with that section gets them.
  A listener declares its exchange, queue and binding, converts the JSON body, acknowledges on return, refuses for good
  on `RejectAndDontRequeueError` or an unreadable body, and tries another failure three times before refusing it. The
  template sends persistent JSON with publisher confirms and tries a fresh connection once.
- `snakeboot.component_scan`: `classes_marked` and `methods_marked` find what decorators marked, like Spring's
  `MethodIntrospector`; `ControllerScan` uses them, and so do the scheduler and the listeners.
- pika's own log messages start at WARNING, so a listener's connection does not fill the log.

## 0.4.0

- `snakeboot.configuration`: a section is a component of the module that declares it. `@configuration_properties`
  puts a wireup provider next to the section, so the section enters the container with its module, like
  `@ConfigurationPropertiesScan`. `Configuration.injectables()` is gone.
- `snakeboot.configuration`: the configuration is read in two steps. `begin_configuration` reads the sections known
  before the container is built (`optional` ones only when their table is there) and leaves the other tables;
  `Configuration.complete` reads everything again with the sections of the container and refuses a table that no
  section claims. `load_configuration` takes both steps at once, as before. `sections_declared_in(module)` finds the

  defaults for the rest. When Django starts, the app reads the sections of the container and, with a database,

- `snakeboot.django_application`: a `DjangoConfigurer` in the component scan or next to the application class adds
  Django apps (`installed_apps`) and middleware (`middleware`, between wireup's and CommonMiddleware), like a
  `WebMvcConfigurer`; snakeboot finds it by reading the source, like an `AppConfig`.
- `snakeboot.rest`: an adapter that extends `BearerAuthentication` is a component of the container, like a
  `SecurityFilterChain` bean; with one in the component scan, every endpoint needs a bearer token it accepts.
- `snakeboot.component_scan`: `ComponentScan.classes_extending(base)` lists the classes written as subclasses of
  `base`, by reading the source.
- `snakeboot.openapi` (standard library only): `@openapi_definition(title, version, description)` describes the

- `snakeboot.component_scan`: `ComponentScan.app_configs()` and `ComponentScan.models()` list the Django `AppConfig`s
  and models under the base packages, by reading the source: nothing is imported, so settings can use them.
- `snakeboot.rest`: `ControllerScan(component_scan).add_to(api)` replaces `RestControllerMounter().mount(api, scan=...)`

- `snakeboot.configuration`: extending `Section` is the contract, as 0.3.0 documented, and it is checked by class.
